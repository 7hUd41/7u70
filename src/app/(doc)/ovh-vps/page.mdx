# Configurer un VPS OVH de zéro

De la commande du serveur dans l'espace client OVH jusqu'à un serveur web durci, prêt à héberger. Renseigne ta config à gauche : chaque commande copiable se remplit automatiquement avec **tes** valeurs.

<Automatic>

```yaml
# playbook.yml — durcissement VPS OVH (rempli avec ta config)
- hosts: ${SERVER_IP}
  become: true
  vars:
    ssh_port: ${SSH_PORT}
    admin_user: ${USERNAME}
  tasks:
    - name: Mettre à jour le système
      apt: { update_cache: true, upgrade: dist }

    - name: Créer l'utilisateur sudo
      user: { name: "{{ admin_user }}", groups: sudo, append: true, shell: /bin/bash }

    - name: Déposer la clé SSH
      authorized_key:
        user: "{{ admin_user }}"
        key: "{{ lookup('file', '~/.ssh/id_ed25519.pub') }}"

    - name: Durcir SSH
      copy:
        dest: /etc/ssh/sshd_config.d/99-hardening.conf
        content: |
          Port {{ ssh_port }}
          PermitRootLogin no
          PasswordAuthentication no
      notify: restart ssh

    - name: Pare-feu — autoriser SSH, HTTP, HTTPS
      community.general.ufw: { rule: allow, port: "{{ item }}", proto: tcp }
      loop: ["{{ ssh_port }}", "80", "443"]

    - name: Activer le pare-feu
      community.general.ufw: { state: enabled }

    - name: Installer fail2ban
      apt: { name: fail2ban, state: present }

  handlers:
    - name: restart ssh
      service: { name: ssh, state: restarted }
```

Lance-le depuis ta machine (Ansible installé en local) :

```bash
ansible-playbook -i ${SERVER_IP}, playbook.yml
```

</Automatic>

## 00 — Architecture cible

<Diagram name="ovh-vps" />

<Detailed>On part d'un VPS Ubuntu fraîchement provisionné chez OVH et on en fait un serveur de production sécurisé.</Detailed>

<Full>Objectif : un utilisateur non-root avec sudo, un accès SSH par clé uniquement sur un port non standard, un pare-feu qui ne laisse passer que l'essentiel, fail2ban contre le brute-force, puis Nginx avec un certificat TLS pour ton domaine. Les étapes marquées « espace client OVH » se font dans l'interface web d'OVH, pas en ligne de commande — elles n'ont donc pas de bouton copier.</Full>

## 01 — Commander le VPS et récupérer les accès

<Detailed>Dans l'espace client OVH, commande un VPS, choisis une image Ubuntu LTS, et — si possible — colle ta clé SSH publique dès la commande.</Detailed>

<Full>OVH t'envoie un email avec l'IP et, selon l'image, un accès root ou un utilisateur par défaut (souvent `ubuntu` ou `debian`). En cas de blocage SSH, tu gardes toujours un accès de secours via la console KVM (« VNC ») directement dans l'espace client OVH — pratique si tu te verrouilles dehors.</Full>

Si tu n'as pas encore de clé SSH sur ta machine locale, génère-en une :

```bash
ssh-keygen -t ed25519 -C "${EMAIL}"
```

<Note>Ta clé **publique** (`~/.ssh/id_ed25519.pub`) se colle dans OVH ou sur le serveur. Ta clé **privée** ne quitte jamais ta machine.</Note>

<Check id="ssh-key" cmd="cat ~/.ssh/id_ed25519.pub" expect="ssh-ed25519 AAAA… ${EMAIL}" />

## 02 — Première connexion

<Detailed>Connecte-toi au serveur avec l'IP fournie par OVH.</Detailed>

```bash
ssh root@${SERVER_IP}
```

<Check id="connexion" cmd="whoami" expect="root" />

<Note>Si ton image OVH utilise un utilisateur par défaut au lieu de root, connecte-toi avec celui-ci (ex. <V name="USERNAME" /> ou `ubuntu`) puis utilise `sudo` pour les commandes suivantes.</Note>

<When is="OS" equals="debian">

<Note>Sur Debian, l'image OVH te connecte généralement directement en `root`. L'utilisateur par défaut `ubuntu` ne s'applique qu'aux images Ubuntu.</Note>

</When>

## 03 — Nom d'hôte et reverse DNS

<Detailed>On nomme la machine, puis on configure le reverse DNS côté OVH pour qu'il corresponde au domaine.</Detailed>

```bash
hostnamectl set-hostname ${HOSTNAME}
```

<Check id="hostname" cmd="hostnamectl --static" expect="${HOSTNAME}" />

<When flag="HAS_DOMAIN">

<Full>Le reverse DNS (enregistrement PTR) ne se règle pas en ligne de commande : dans l'espace client OVH, ouvre la fiche du VPS et définis le reverse DNS de l'IP sur ton domaine (ex. <V name="DOMAIN" />). C'est important pour la délivrabilité des emails et la réputation du serveur.</Full>

</When>

## 04 — Mise à jour du système

<Detailed>On récupère et applique toutes les mises à jour avant de continuer, et on fixe le fuseau horaire.</Detailed>

```bash
apt update && apt upgrade -y
```

```bash
timedatectl set-timezone Europe/Paris
```

<Check id="timezone" cmd="timedatectl | grep 'Time zone'" expect="Time zone: Europe/Paris (CEST, +0200)" />

<Full>Le `-y` répond oui automatiquement. Si le noyau est mis à jour, un redémarrage (`reboot`) peut être nécessaire — reconnecte-toi ensuite avec la même commande SSH.</Full>

## 05 — Créer un utilisateur sudo

<Detailed>On crée un compte dédié, on lui donne les droits sudo, et on lui copie ta clé SSH.</Detailed>

<Full>Travailler en root au quotidien est risqué : une seule faute de frappe peut casser tout le système. On crée donc un utilisateur dédié, on le place dans le groupe `sudo` pour élever les droits ponctuellement, et on recopie la clé SSH déjà présente afin de pouvoir se connecter directement avec ce compte.</Full>

```bash
adduser ${USERNAME}
usermod -aG sudo ${USERNAME}
```

```bash
rsync --archive --chown=${USERNAME}:${USERNAME} ~/.ssh /home/${USERNAME}
```

<Check id="user-sudo" cmd="groups ${USERNAME}" expect="${USERNAME} : ${USERNAME} sudo" />

## 06 — Sécuriser SSH

<Detailed>Trois réglages : changer le port, interdire le login root, et n'autoriser que les clés.</Detailed>

<Full>Déplacer SSH sur un port non standard réduit énormément le bruit des bots ; interdire root et les mots de passe ferme les deux principales portes d'entrée du brute-force. Édite le fichier `/etc/ssh/sshd_config` et modifie (ou décommente) ces trois lignes :</Full>

```ini
Port ${SSH_PORT}
PermitRootLogin no
PasswordAuthentication no
```

```bash
systemctl restart ssh
```

<Warn>Garde ta session actuelle ouverte et teste la nouvelle connexion dans un **autre** terminal. Si elle échoue, tu corriges sans être verrouillé dehors.</Warn>

```bash
ssh -p ${SSH_PORT} ${USERNAME}@${SERVER_IP}
```

<Check id="ssh-hardening" cmd="sudo sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication) '" expect={"port ${SSH_PORT}\npermitrootlogin no\npasswordauthentication no"} />

## 07 — Pare-feu UFW

<Detailed>On n'ouvre que SSH (ton nouveau port), HTTP et HTTPS.</Detailed>

```bash
ufw allow ${SSH_PORT}/tcp
```

<Warn>Autorise ton port SSH **avant** d'activer UFW, sinon `ufw enable` te coupe l'accès immédiatement.</Warn>

```bash
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
```

<Check id="ufw" cmd="ufw status" expect={"Status: active\n${SSH_PORT}/tcp   ALLOW   Anywhere"} />

<Note>OVH propose aussi un pare-feu réseau (« Network Firewall ») configurable dans l'espace client, en amont du serveur. UFW suffit pour commencer ; le pare-feu OVH est un bonus pour bloquer en périphérie.</Note>

## 08 — Fail2ban

<Detailed>Bannit automatiquement les IP qui enchaînent les échecs de connexion.</Detailed>

```bash
apt install fail2ban -y
```

<Full>Fail2ban lit les logs et bannit temporairement toute IP qui multiplie les tentatives ratées. Crée le fichier `/etc/fail2ban/jail.local` pour surveiller ton port SSH personnalisé :</Full>

```ini
[sshd]
enabled = true
port = ${SSH_PORT}
maxretry = 3
bantime = 1h
```

```bash
systemctl restart fail2ban
```

<Check id="fail2ban" cmd="systemctl is-active fail2ban" expect="active" />

<When flag="HAS_DOMAIN">

## 09 — Nginx et HTTPS

<Detailed>Serveur web + certificat TLS gratuit (Let's Encrypt) pour ton domaine.</Detailed>

<Full>Avant cette étape, ton domaine doit pointer vers le serveur : dans ta zone DNS (chez OVH ou ton registrar), crée un enregistrement A faisant pointer <V name="DOMAIN" /> vers <V name="SERVER_IP" />. Une fois la propagation faite, Certbot peut obtenir le certificat.</Full>

```bash
apt install nginx certbot python3-certbot-nginx -y
```

```bash
certbot --nginx -d ${DOMAIN} -m ${EMAIL} --agree-tos --redirect
```

<Check id="https" cmd="curl -sI https://${DOMAIN} | head -n1" expect="HTTP/2 200" />

<Note>Certbot configure le HTTPS, la redirection HTTP → HTTPS, et le renouvellement automatique du certificat. Plus rien à faire ensuite.</Note>

</When>

## 10 — Sauvegardes et mises à jour auto

<Detailed>On active les mises à jour de sécurité automatiques, et on pense aux snapshots OVH.</Detailed>

```bash
apt install unattended-upgrades -y
dpkg-reconfigure -plow unattended-upgrades
```

<Check id="auto-updates" cmd="systemctl is-active unattended-upgrades" expect="active" />

<Full>Côté sauvegarde, l'espace client OVH propose des snapshots ponctuels et une option de sauvegarde automatique du VPS. Active-la : c'est ta bouée si une manipulation tourne mal.</Full>

## 11 — Vérifications finales

<Detailed>On vérifie que tout tient debout.</Detailed>

```bash
ssh -p ${SSH_PORT} ${USERNAME}@${SERVER_IP}
ufw status
systemctl status fail2ban
```

<Check id="final" cmd="ssh -p ${SSH_PORT} ${USERNAME}@${SERVER_IP} 'ufw status | head -n1; systemctl is-active fail2ban'" expect={"Status: active\nactive"} />

<Full>Si la connexion passe sur ton port personnalisé avec ton utilisateur, que UFW est actif et que fail2ban tourne, ton VPS OVH est durci et prêt à héberger. Bonne mise en prod.</Full>
